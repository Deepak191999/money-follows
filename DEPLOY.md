# Deploying the review build

Two services: the Node backend and the React frontend as a static site.
`render.yaml` in the repo root describes both.

Every build and start command here was run against a clean copy of this repo — no
`node_modules`, no `dist`, no `data.db` — and verified end to end: build, seed, production
start, login, invitation, outbox, and a cross-origin request from the frontend origin.

## 1. Push to GitHub

Render builds from a repository, and this folder is not one yet.

```bash
git init
git add .
git commit -m "Money Follows: dark mode and email invitations"
git branch -M main
git remote add origin https://github.com/<you>/money-follows.git
git push -u origin main
```

`.gitignore` already excludes `node_modules/`, `dist/`, `*.db`, `*.log` and `.env`.
Nothing secret is committed: `JWT_SECRET` is generated by Render.

## 2. Create the services

1. Render dashboard → **New** → **Blueprint**.
2. Pick the repository. Render reads `render.yaml` and proposes two services:
   `money-follows-api` and `money-follows-web`.
3. **Apply**. The first build takes a few minutes.

## 3. Fix the two URLs, then redeploy

Neither service can know the other's URL before both exist, so the values committed in
`render.yaml` are placeholders. After the first deploy, note the two real URLs and set:

| Service | Variable | Value |
|---|---|---|
| `money-follows-api` | `APP_URL` | the **frontend** URL, e.g. `https://money-follows-web.onrender.com` |
| `money-follows-web` | `VITE_API_BASE` | the **backend** URL, e.g. `https://money-follows-api.onrender.com` |

Edit them in `render.yaml` and push, or set them in each service's **Environment** tab.
Then redeploy both.

**Get `APP_URL` right or the feature looks broken.** It is what invitation links are built
from. Unset, it falls back to `http://localhost:5173` and every emailed link is dead for
anyone but you. `VITE_API_BASE` is baked in at build time by Vite, so changing it needs a
rebuild, not just a restart.

## 4. Check it works

Open the frontend URL and confirm:

- [ ] Login as `asha@example.com` / `password123` succeeds (proves `VITE_API_BASE`)
- [ ] The theme button cycles System → Light → Dark and survives a reload
- [ ] **What I built** in the nav explains both features
- [ ] Inviting `bilal@example.com` to Goa trip adds him immediately
- [ ] Inviting an unused address shows a pending invitation
- [ ] The dev link in that message starts with your **frontend** URL, not localhost
- [ ] `<backend>/dev/outbox` lists the invitation email
- [ ] Opening the invite link in a private window shows the signup form

## What reviewers should know

**First load is slow.** Free Render web services sleep after ~15 minutes idle; the next
request can take 50 seconds or so while the container wakes. The static frontend does not
sleep, so the page appears instantly and then waits on the API. Warm it up before demoing.

**Data resets.** The database is SQLite inside the container, seeded at image build. There
is no persistent disk on the free plan, so any restart or redeploy returns it to the three
seed users and two groups. That is convenient for a review and wrong for anything else.

**`/dev/outbox` is public on this deployment.** `ENABLE_DEV_OUTBOX=true` is what lets
reviewers read the invitation emails, and it means anyone with the URL can read every
invite link. Acceptable for throwaway seed data; it must be off for real users, which is
why it defaults to off whenever `NODE_ENV=production`.

**No real mail is sent.** `MAIL_TRANSPORT=outbox` stores messages in the database.
Switching to `smtp` throws on send rather than silently dropping invitations, so a real
provider has to be wired up deliberately.

## Alternative: Vercel plus Render

If you would rather host the frontend on Vercel or Netlify, only the static half changes:

- Root directory `frontend-react`, build `npm run build`, output `dist`
- Environment variable `VITE_API_BASE` = your backend URL
- Add an SPA rewrite of `/*` to `/index.html`, or `/invite/<token>` will 404

The backend stays on Render exactly as above.

## Why not the Dockerfile

`backend-node/Dockerfile` works and would also deploy fine, but `render.yaml` uses
Render's native Node runtime instead: one less layer to debug if a build fails, and it is
the path verified from a clean tree here. Note the `--include=dev` in the build command —
`NODE_ENV=production` is set on the service, which would otherwise make `npm ci` skip
`typescript` and `tsx`, and both are needed to compile and seed.

## If you want the simplest possible alternative

Frontend on Vercel, backend on Render, is the same amount of work and both have generous
free tiers. The only values that matter either way are `VITE_API_BASE` on the frontend and
`APP_URL` on the backend, pointing at each other.
